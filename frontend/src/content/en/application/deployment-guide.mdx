# Deployment Guide

Matrix-Law uses one deployment entry point: `deploy/two-server/` in the
Matrix-Law repository. The repository's local mode runs two containers that model
independent servers. It is designed for development and candidate acceptance; it is
not a production installer.

## Cloud target architecture

The production target is native processes managed by systemd on two independent
Linux hosts. The capability host manages the Gateway, operations console, model
relay, PostgreSQL, and Redis. The law-firm host manages the lawyer workspace, firm
administration, legal extension, private OCR, PostgreSQL, Redis, object storage, and
Nginx. The two hosts keep their databases and Redis instances separate. Native
release tooling is still a prototype; the target hosts, Linux distribution,
production secret store, and cross-host acceptance have not been completed.

## Start and stop the local candidate

Run these commands from the repository root:

```bash
./scripts/bootstrap.sh
./scripts/doctor.sh
./deploy/two-server/start.sh
```

The start script accepts `TWO_SERVER_DEPLOYMENT_MODE=local-candidate`. It creates
runtime credentials in a private, permission-restricted directory on first setup.
Keep that directory outside source control and do not expose its contents.

| Service | Local URL |
| --- | --- |
| Capability operations | `http://127.0.0.1:4110/console/` |
| Law-firm administration | `http://127.0.0.1:4111/law-admin/` |
| Lawyer workspace | `http://127.0.0.1:4111/login` |

Stop services without deleting local data:

```bash
./deploy/two-server/stop.sh
```

## Data and credential boundaries

The capability and tenant containers have separate PostgreSQL databases, Redis
instances, and service credentials. Platform model and supplier credentials belong
to the capability side. Legal materials, OCR results, citations, and lawyer review
belong to the tenant data domain. Tenant snapshots must not contain provider keys or
reusable platform credentials.

The local runtime directory contains private keys, certificates, passwords, and
generated environment files. Keep its permissions restricted and never commit or
copy it into documentation, support bundles, or logs. The local candidate uses local
PKI and credentials; it does not demonstrate production KMS, secret rotation, or
recovery.

## Production acceptance

The local start script rejects production mode and must not be used to initialize
production accounts. Before a production deployment, separately establish and
evidence:

- two independently managed hosts, production PKI, secret storage, rotation, and MFA;
- data-processing, retention, residency, and human-review requirements for every
  external provider and legal-material path;
- signed release artifacts, encrypted off-site backups, and a restore exercise;
- production-equivalent load, monitoring, alert delivery, access controls, and
  incident operations;
- real-law-firm workflow and legal-quality acceptance, billing reconciliation, and
  customer support and exit procedures.

Local HTTP checks, synthetic tests, and healthy containers are candidate evidence
only. They do not establish these production gates.
